# 고전한입 관리자 · Classic Bites Admin

고전한입의 책·작품·목차·학습 본문을 관리하는 독립 관리자 프로젝트입니다. 원격 저장소는 `xixirepository/classic-bites-admin`이며, iOS 앱과 콘텐츠 API는 각각 별도 저장소에서 관리합니다.

서재 최상위에는 사서오경을 한 권으로 표시합니다. 대학·중용 등은 사서오경 내부 작품이며, 관리자가 다른 책을 등록·공개하면 iOS가 콘텐츠 API를 다시 조회하여 표시합니다. 작품 구분이 없는 책에는 장을 바로 등록할 수 있습니다.

사용자가 선택한 기술은 Python·FastAPI로 제공하는 관리자 화면과 HTML·CSS·JavaScript입니다. 프런트엔드 프레임워크는 추가하지 않습니다. 기존 FastAPI 백엔드가 MySQL 콘텐츠와 MinIO 표지를 관리하며 이 프로젝트는 관리 API를 호출합니다. 관리자 서버에 데이터베이스나 MinIO 자격증명을 복제하지 않습니다.

## 구현 상태

- 기존 이메일·비밀번호 인증을 이용하는 관리자 로그인과 로그아웃.
- 책 → 내부 작품(선택) → 장 → 한입 탐색, 각 항목의 추가·수정·노출 순서·공개 여부 관리.
- 책·작품 소개와 표지 업로드, 한입의 원문·번역·해설 편집 및 확인.
- 목록 새로고침, 빈 목록·통신 오류·재시도 안내, 미저장 변경 이탈 확인, 중복 저장 방지.
- 관리자 API 권한 검사, 메모리 내 토큰 보관, 만료 후 재로그인 안내와 작성 중인 폼 유지.

관리자 회원 생성·권한 부여·Google 로그인·비밀번호 재설정 화면은 구현하지 않았습니다. 콘텐츠 삭제와 부모 변경도 현재 화면의 범위에 포함하지 않습니다. 운영 관리자 주소·HTTPS 배포 방식은 미정이며 **콘텐츠 API와 관리자 화면은 운영 서버에 아직 배포하지 않았습니다.** 기존 운영 API의 인증 배포와 이번 콘텐츠 기능 배포를 구분합니다.

| 파일 | 역할 |
| --- | --- |
| `admin/main.py` | 관리자 정적 화면, 공개 연결 설정, 보안 응답 헤더 제공 |
| `admin/static/index.html` | 한국어 로그인·관리 화면 구조 |
| `admin/static/app.js` | 인증, API 조회·저장, 편집 상태와 표지 처리 |
| `admin/static/styles.css` | 작은 북라운지 스타일과 좁은 화면 배치 |
| `requirements.txt`, `requirements-test.txt` | 서버 및 검증 의존성 |
| `scripts/check-admin.py` | 연결 주소·응답 헤더·정적 파일 제공 검사 |
| `scripts/check-admin-ui.cjs` | 비동기 확인창·미저장 변경·공개 취소 회귀 검사 |

## 로컬 실행

Python 3.13을 사용합니다. 아래 명령은 이 저장소 루트에서 실행합니다.

```sh
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt

# 별도로 준비한 로컬 콘텐츠 백엔드 주소
export ADMIN_API_BASE_URL=http://127.0.0.1:18000
.venv/bin/uvicorn admin.main:app --host 127.0.0.1 --port 18765
```

실행한 동안 [로컬 관리자 화면](http://127.0.0.1:18765/admin)을 엽니다. 종료는 실행 터미널에서 `Ctrl+C`를 누릅니다. 이 명령은 관리자 화면 서버만 시작하며, 백엔드·MySQL·MinIO 또는 관리자 계정을 자동으로 준비하지 않습니다. 검증용으로 잠시 실행한 로컬 서버는 상시 서비스가 아닙니다.

`ADMIN_API_BASE_URL`은 브라우저가 호출할 **백엔드 원점**입니다. 스킴·호스트·선택적 포트만 지정하며 경로, 쿼리, 자격증명을 넣지 않습니다. HTTPS를 사용하고 개발용 HTTP는 loopback 호스트만 허용합니다. `.env.example`은 참고용이며 이 서버가 `.env`를 자동으로 읽지는 않으므로 실행 환경에 명시적으로 설정합니다.

설정을 생략하면 기존 운영 인증 API 주소 `https://vpn.xixiplay.com`을 사용합니다. 해당 기본 주소가 있다고 해서 새 콘텐츠 API가 배포되었다는 뜻은 아닙니다. 로컬 검증에는 위처럼 별도로 준비한 테스트 백엔드를 지정합니다. `/config.json`에는 API 주소만 제공하며 비밀번호·토큰·DB·MinIO 키를 넣지 않습니다.

## 백엔드와 관리자 권한 준비

별도 `classic-bites-backend` 저장소의 `docs/auth-api.md`, `docs/catalog-api.md`에 따라 인증과 콘텐츠 스키마·API를 먼저 준비합니다. 백엔드의 `AUTH_ENABLED`, `CATALOG_ENABLED`가 활성화되어 있어야 하며, 기존 회원·미디어와 데이터 볼륨을 유지합니다.

1. 기존 인증 API의 이메일·비밀번호 계정을 준비합니다. 신규 계정이 필요하면 백엔드의 기존 회원가입 절차를 사용합니다. 이 관리자 화면에는 최초 관리자 생성 화면이 없습니다.
2. 해당 회원의 안정적인 UUID를 백엔드의 비공개 `CATALOG_ADMIN_USER_IDS` 설정에 등록합니다. 표시 이름이나 이메일만으로 관리 권한을 부여하지 않습니다. 여러 UUID는 쉼표로 구분합니다.
3. 브라우저에서 여는 관리자 화면의 정확한 원점을 백엔드 `CATALOG_ADMIN_ORIGINS`에 등록합니다. 아래는 로컬 실행 예시입니다.

```dotenv
# 아래 설정은 관리자 서버가 아니라 콘텐츠 백엔드에 적용합니다.
CATALOG_ADMIN_USER_IDS=USER_UUID_PLACEHOLDER
CATALOG_ADMIN_ORIGINS=http://127.0.0.1:18765
```

`USER_UUID_PLACEHOLDER`는 실제로 권한을 부여할 기존 회원 UUID로 서버에서 바꿉니다. 실제 계정 정보나 자격증명을 README·저장소·로그에 기록하지 않습니다. 설정 적용은 백엔드 문서의 실행 방식에 따릅니다.

`http://localhost:18765`와 `http://127.0.0.1:18765`는 서로 다른 원점입니다. 실제 접속 주소를 정확히 등록하며 `/admin` 같은 경로나 와일드카드를 사용하지 않습니다. 공개 환경에는 운영 관리자 HTTPS 원점을 지정해야 합니다.

**Google로만 가입한 계정은 이 화면의 이메일·비밀번호 로그인으로 인증할 수 없습니다.** 현재 백엔드는 Google 계정에 비밀번호를 추가하거나 같은 이메일의 다른 로그인 방식을 자동 연결하지 않습니다. 기존 이메일·비밀번호 계정을 준비해 관리자 UUID로 지정해야 합니다. 이 제한을 우회하려고 사용자 인증 방식이나 기존 계정을 변경하지 않습니다.

## 공개와 앱 반영

새 항목은 기본적으로 비공개입니다. 각 단계의 공개 설정은 독립적이며, 앱에는 자신과 상위 책·작품·장이 모두 공개된 항목만 보입니다. 상위를 비공개로 전환해도 하위 항목의 저장된 설정은 유지됩니다. 이후 상위를 다시 공개하면 하위의 기존 공개 설정이 적용됩니다.

`읽기 가능`은 서버가 계산한 상태입니다. 자신과 모든 상위 항목이 공개되어 있고, 원문·번역·해설 중 하나 이상에 텍스트가 있는 공개 한입이 있어야 합니다. 관리자가 직접 준비 상태를 바꾸지는 않습니다. 공개했지만 본문이 없는 책·작품·장은 탐색할 수 있고, 빈 한입은 준비 중으로 표시됩니다. 비공개 초안은 내용이 있어도 독자가 읽을 수 있는 상태로 계산되지 않습니다.

저장·공개·노출 순서 변경은 앱이 다음에 콘텐츠 API를 조회할 때 반영됩니다. 앱의 새로고침 또는 해당 목록 재진입으로 확인하며, 열려 있는 화면에 실시간으로 밀어 넣는 기능은 없습니다. 새 책을 추가하기 위해 앱의 정적 목록을 수정하거나 앱을 다시 배포할 필요는 없습니다.

표지는 책·작품을 저장한 뒤 별도로 업로드합니다. PNG·JPEG·WebP, 최대 5 MiB를 지원합니다. 원문·번역·해설은 텍스트로 편집하며, 이용 권리와 검수를 확인한 내용을 입력합니다. 샘플이나 빈 콘텐츠를 검수된 고전 본문으로 표시하지 않습니다.

## 인증과 브라우저 보관

- access/refresh token은 현재 페이지의 메모리에만 둡니다. `localStorage`, `sessionStorage`, URL에 저장하지 않습니다. 전체 페이지 새로고침·새 창 열기에는 다시 로그인해야 합니다.
- API 요청은 `Authorization: Bearer`를 사용하고 `credentials: omit`으로 쿠키 인증을 사용하지 않습니다. 현재 방식은 브라우저가 쿠키를 자동 첨부하는 인증에 의존하지 않으며, 별도의 쿠키 기반 CSRF 토큰 방식은 구현하지 않았습니다.
- 백엔드는 매 관리 요청에서 세션과 관리자 UUID를 검사합니다. 정확한 원점만 허용하는 CORS는 이 권한 검사를 대신하지 않습니다.
- 세션을 자동 갱신하지 않습니다. 만료 시 토큰을 비우고 재로그인을 안내하며, 화면에 남은 작성 내용을 이어갈 수 있습니다. 전체 페이지 새로고침은 초안을 보존하지 않습니다.
- 로그아웃·만료 시 기존 refresh token의 서버 해제를 시도합니다. 로그아웃 통신이 실패해도 로컬 토큰은 비우고 서버 해제 미확인 안내를 표시합니다.
- 표지 미리보기도 관리자 인증으로 읽어 임시 blob URL로 표시하고 화면 교체·로그아웃 때 해제합니다. 사용자 입력은 실행 가능한 HTML로 삽입하지 않습니다.
- 관리자 서버는 `no-store`, 프레임 삽입 거부, 외부 스크립트 차단과 지정된 API 원점만 허용하는 CSP를 적용합니다.

## 검증과 남은 확인

검증 의존성과 명령은 다음과 같습니다. JavaScript 문법 확인에는 Node.js가 필요하지만 화면 실행 자체에 Node.js 서버는 필요하지 않습니다.

```sh
.venv/bin/python -m pip install -r requirements-test.txt
.venv/bin/python scripts/check-admin.py
node --check admin/static/app.js
node scripts/check-admin-ui.cjs
git diff --check
git status --short
```

2026-09-30 Python 3.13 가상환경에 검증 의존성을 설치하고 서버 검사, JavaScript 문법 검사, 변경 공백 검사를 통과했습니다. 서버 검사는 허용·거부할 API 원점, 공개 설정의 내용, 제공 파일 제한, 보안 응답 헤더를 확인합니다. `scripts/check-admin-ui.cjs`의 8개 검사는 실제 화면 스크립트를 격리된 모의 DOM에서 실행해 확인창의 취소·Escape·중복 요청 차단, 미저장 변경 보존, 승인 시 한 번만 저장, 만료 시 취소, 본문·표지 용량 오류 구분을 확인합니다. 브라우저 자체의 렌더링 검사를 대신하지 않습니다.

별도의 로컬 통합 검증에서 다음을 확인했습니다.

- 관리자 브라우저 로그인 → 사서오경 → 대학 → 장·한입 등록과 원문·번역·해설의 테스트 MySQL 저장, iOS 읽기 화면 표시.
- 새 책 ‘손자병법’ 등록·공개 후 iOS 서재 목록에 동적으로 표시.
- 브라우저 파일 선택으로 표지 두 장을 차례로 업로드하고 실제 테스트 MinIO의 표지 읽기 성공, iOS 재진입 후 교체된 표지 표시.
- Chrome에서 공개 전환 확인창의 Escape 취소와 키보드 승인, 승인 후 실제 API 저장·목록 반영.
- 상위 책을 비공개로 바꾼 뒤 책·장·한입·표지 직접 조회 차단, iOS 재조회 시 서재에서 제거, 일반 회원의 관리 API 접근 거부.

검증은 임시 로컬 환경에서 수행했으며 운영 배포·실제 관리자 계정·사용자의 iPhone 확인을 대신하지 않습니다. 백엔드의 상세 검증 결과는 해당 저장소 기록을 따릅니다.

사용자 확인에는 관리자가 새 책과 본문을 등록·공개한 뒤 iOS에서 새로 조회하여 읽는 동선, 수정·비공개 전환 반영, 표지 표시, 로그인 만료·재로그인을 포함합니다. 현재는 자동 검증 후 사용자 테스트와 통합 승인 전 단계입니다. 운영 배포·push는 실행하지 않았습니다.

## 작업 정책

[AGENTS.md](AGENTS.md)를 먼저 읽고 로컬 `dev`에서 작업 브랜치를 만듭니다. 구현과 자동 검증 후 사용자 테스트 확인을 받으며, 승인 전 통합용 rebase·squash·병합을 하지 않습니다. push는 사용자가 직접 수행합니다.
